# Обязательное правило проекта: одно ядро, два равноправных способа управления

Решение владельца от 28.11.2026. Идентификатор требования: CORE-DUAL-01. Имеет приоритет над прежними предположениями о пользовательских сценариях, применяется ко всем существующим и новым функциям Мастерской, в том числе к интеграциям, учёту и планированию.

## 1. Полная функциональная эквивалентность

Каждая пользовательская функция должна быть доступна двумя независимыми способами:
- Только через кабинет Мастерской: формы, кнопки, отчёты и настройки, без использования чата и без вызова модели.
- Только через чат Подмастерья: пользователь получает данные, задаёт параметры, выполняет операции, изменяет настройки, подтверждает изменения, проверяет статус и получает результат, не переходя в разделы кабинета ради выполнения бизнес-операции.

Ни один режим не требует другого для завершения обычной пользовательской операции. Чат — полноценный способ управления, а не навигатор по разделам; кабинет — полноценная программа, а не интерфейс для отправки промптов. Область доступных операций определяется ролью и разрешениями владельца, а не способом управления. Секреты вводятся в защищённые поля (допустимо встроенное защищённое поле прямо в чат), не передаются модели и не сохраняются в обычной переписке. Обязательная аутентификация и защитные подтверждения не обходятся через чат. Внутренние служебные операции исполнителя не становятся доступными пользователю только из-за этого требования.

## 2. Одна архитектура, не две реализации

У каждой операции один авторитетный серверный контракт (ID, версия, схема входа/выхода, эффект, права, обработчик), общие расчётные функции, единый исполнитель, одни авторитетные данные и одни правила валидации, подтверждения, идемпотентности, транзакций, журналирования, ошибок и восстановления. UI и чат — адаптеры ввода и представления результата; они преобразуют ввод в один и тот же типизированный запрос. Данные и настройки, изменённые через один канал, сразу доступны через другой после штатного обновления. Запрещено создавать параллельные бизнес-правила, формулы, обработчики, таблицы состояния или отдельную систему шаблонов для ИИ. Допустимы представления и производные кэши над авторитетными данными, но не второй источник истины.

Сбор истории, пагинация, нормализация, расчёты, очереди, повторы, контроль полноты, обновление коэффициентов, формирование отчётов выполняются скриптами. UI вызывает их напрямую; однозначные команды чата маршрутизируются локальной матрицей, а DeepSeek при необходимости интерпретирует свободную формулировку, выбирает тот же инструмент, передаёт параметры и объясняет его результат. UI не использует модель для бизнес-операций. Не отправлять ключи, сырые страницы API, внутренние очереди и весь каталог низкоуровневых методов модели. Смена/недоступность модели или отсутствие монет не блокирует локальные функции кабинета. Расчёт и синхронизация не потребляют монеты за ИИ; свободная команда тарифицируется только за фактическое обращение к модели по штатным правилам.

## 3. Полный жизненный цикл операции

Обеспечить обоим каналам: создание, чтение, изменение, допустимое удаление/архивирование, предпросмотр, подтверждение или отмену, поиск, фильтрацию, экспорт, настройку коэффициентов, управление интеграциями, запуск и остановку разрешённых задач, наблюдение прогресса, диагностику ошибок и повтор/возобновление. Для длительных операций общий идентификатор задания, durable-состояние, правила остановки, результаты и квитанции; закрытие вкладки или чата не отменяет серверную задачу само по себе. Повтор операции из другого канала по тому же идентификатору не дублирует записи или списания. При отсутствии данных показывать одинаковый статус неполноты, не придумывать нули. Не подменять реальные изменения словами о выполнении.

## 4. Обязательная приёмка каждого релиза

| ID | Критерий |
|---|---|
| DUAL-01 | Реестр всех пользовательских операций в области релиза сопоставлен с элементом UI и доступным инструментом/командой чата. Нет операций, которые доступны только в одном канале. |
| DUAL-02 | На одинаковых исходных данных и параметрах оба входа вызывают один авторитетный обработчик и дают эквивалентный результат, состояние БД и квитанцию. |
| DUAL-03 | Полный сценарий через кабинет при отключённом DeepSeek и отсутствии монет; ноль вызовов модели. |
| DUAL-04 | Полный сценарий через чат без открытия разделов кабинета; все обязательные поля, разрешения и подтверждения соблюдены. |
| DUAL-05 | Взаимная видимость изменений, одинаковые ошибки, отмена, восстановление и защита от дублей, включая смену канала во время работы с задачей. |
| DUAL-06 | Проверены одинаковая изоляция клиентов, роли, запреты и безопасный ввод секретов. |
| DUAL-07 | Ревью исходников подтверждает отсутствие дублирующих расчётов и параллельной архитектуры; оба пути используют общий контракт и ядро. |
| DUAL-08 | Каждая новая функция сразу проектируется и реализуется для обоих способов управления. Неполный паритет отмечается как дефект/блокер, а не как принятая функция. |

Это правило является воротами приёмки, а не утверждением о том, что текущий production уже удовлетворяет всем критериям. Существующие функции проверяются на соответствие; неподтверждённые сценарии включаются в очередь доработки.
