# Контракты поставщиков мониторинга закупочных цен

Дата проверки первичных источников: **28 ноября 2026 года**. Документ относится к единому кандидату Мастерской, а не к production. Публичные описания API проверены веб-поиском и чтением официальных страниц; платные вызовы при подготовке этого документа не выполнялись.

## 1. Решение по транспортам

| Источник товара | Штатный путь | Условие допуска |
|---|---|---|
| Ozon | существующий `parser_market.orders`, `market=ozon` | одна точная карточка, подтверждённые ключ/квота/тариф, резерв в общем billing, действующее разрешение запуска |
| Wildberries | тот же адаптер, `market=wb` | те же условия; размер принимается только при подтверждении идентификатора варианта в отчёте |
| Яндекс Маркет | тот же адаптер, `market=ym` | Москва; точная карточка либо точные modelid+skuid; продавец и вид цены уточняются при неоднозначности |
| Обычный публичный магазин | общий native model gateway, отдельный типизированный route, DeepSeek Flash + `deepseek_read_url`, thinking disabled | **отправка закрыта**: нет доказанного суммарного финансового предела запроса и доказанного ограничения цепочки перенаправлений |

Для обычных сайтов в штатный gateway встроены только типизированный контракт допуска и чтение его статуса. Рабочее платное исполнение native Read URL пока не реализовано; чистые функции формирования запроса и разбора ответа не заменяют reserve/dispatch/usage/settlement. Наличие библиотеки и успешных автономных тестов не выдаётся за выполненную живую проверку. Закрытый допуск возвращает `contract_blocked`, не создаёт provider attempt и не превращает неизвестную стоимость в нулевую фактическую стоимость.

## 2. parser.market: подтверждённый внешний контракт

### Точные товарные методы

[Документация методов](https://parser.market/dokumentacziya/) различает карточки, поиск и дополнительные предложения. В мониторинге используются только `ozon`, `wb`, `ym` с одной ссылкой `linkset`. Поставщик указывает одну проверку на ссылку, включая Яндекс `/p/…/modelid/skuid` с первыми десятью предложениями и `/card/…/id`. Для Яндекс поддерживается только Москва. `donotsearch` не используется как универсальная гарантия отсутствия поиска: в части методов поле игнорируется или служебное.

Локальная проверка принимает точные домены и формы URL. Поиск, категории, сокращённые ссылки, неподдерживаемые поддомены, credentials, private query keys и IP-адреса не отправляются. Идентификаторы и выбранный размер сохраняются; tracking-параметры исключаются. Старые Яндекс `/product--…/id` описаны в [официальном руководстве Яндекс-парсера](https://parser.market/parser-czen-yandeks-market/), но их актуальность требует живой проверки. Исторические `glfilter` не отбрасываются молча: URL с таким ограничением отклоняется до отправки, поскольку оно может определять упаковку независимо от SKU.

### Приём, восстановление, баланс

[Официальный JSON API](https://parser.market/parser-cen-json-api/) задаёт POST-методы `get-balanse`, `send-order`, `get-last50` под фиксированным `https://parser.market/wp-json/client-api/v1/`. В действующем примере `name` — непустая строка; `linkset` — массив строк. Ответ `success` подтверждает получение задания, а не завершение обработки. Немедленный order ID не гарантирован. Для поиска исходного задания используется собственная метка `userlabel` длиной до 20 символов. Поле `checks_total` уже учитывает вычет ожидающих заданий; повторный вычет `checks_pending` ошибочен.

Исправлены два существовавших дефекта общего адаптера: метка теперь `PM` плюс 18 hexadecimal символов, и проверка доступного баланса больше не вычитает pending второй раз. Это изменение охватывает прежние `search/cards/reviews` и проверено их регрессиями. При потере ответа после dispatch продолжается чтение исходного задания с прежней меткой. Повторная покупка под новой меткой не выполняется.

### Фактическая тарификация

[Прайс поставщика](https://parser.market/czeny/) содержит базовую стоимость проверки и объёмные скидки, которые зависят от аккаунта. Число позиций не является надёжным показателем фактического списания. [Описание отчётов](https://parser.market/zadaniya-i-otchety/) определяет `used_checks_total` как фактически использованные проверки задания; также описывает `Price`, `PromoPrice`, `OldPrice`, продавца и фильтры предложений.

**Локальная финансовая формула:** максимальный объём точного однотоварного запроса — одна проверка; денежный предел вычисляет существующий `service_billing.quote` из действующей версии клиентского тарифа и проверенной конфигурации аккаунта. Окончательное списание строится из исходной квитанции и её `used_checks_total`, а не из числа предложений, выбранной товарной цены или локального предположения о скидке. Общий wallet, service attempts, общий реестр цен, административная сверка и исходная provider account binding остаются источниками финансовых данных.

Если квитанция отсутствует, содержит неподдерживаемый тип величины, относится к другой метке/заказу либо превышает резерв, результат не считается окончательно оплаченным: остаётся ожидание или финансовый конфликт. Дробная величина проверок пока не интерпретируется как целая; такая реальная квитанция потребует расширения общего финансового контракта, а не округления адаптером.

### Значение товарной цены

Это локальные правила принятия результата, не обещания поставщика:

- `Price` и `PromoPrice` имеют разный смысл; `OldPrice` никогда не становится текущей ценой. Несколько продавцов/типов цены вызывают предметное уточнение.
- До принятия результата проверяются код строки, исходное имя корреляции, регион и идентичность карточки/SKU/размера. Смешанный ответ с другим товаром не фильтруется до удобного совпадения.
- Фильтры, включая массив `values`, входят в основу сравнения. Изменение упаковки, варианта, продавца или условий не объединяется с прежней серией цен.
- Идентификатор выбранного варианта вычислен из смысла цены, без её числового значения. Поэтому новая цена той же позиции принимается без фиксации старого числа в инструкции.
- JSON дроби читаются через `Decimal`, компактный результат хранит точную десятичную строку. Формат согласован с доменом: до 18 цифр целой части и 18 после запятой; превышение — отказ от результата, не округление. Это ограничение локального формата, не тарифный предел.
- В результат не попадают полный отчёт, описания, фотографии, reviews, токены или API key. Название, seller, terms считаются недоверенными текстовыми данными. В модель marketplace-отчёт не передаётся.

## 3. Общий координатор запросов

`parser_market.orders` использует существующие `market_rate_limit.acquire/release/cooldown` и таблицы `market_data_quota/market_data_permits`. Ключ лимита связан с подтверждённым аккаунтом поставщика, а не с cookie или пользователем. Старые сохранённые parser cooldown мигрируются; прежняя таблица не участвует в новых допусках.

Числовой публичный QPS-контракт parser.market не найден. Одна одновременно выполняемая операция на аккаунт и экспоненциальный backoff — **локальная защитная политика**, не приписанный поставщику лимит. HTTP `Retry-After` обрабатывается и в секундах, и как HTTP-date общим координатором. Ожидание записывается как срок следующей попытки: worker не спит и не держит транзакцию. Успешный шаг освобождает permit; аварийный permit имеет конечный срок.

До платной отправки временный сбой чтения баланса (`408`, `429`, `5xx`, timeout/reset/temporary DNS) получает не более пяти попыток через этот же координатор. Это локальное ограничение повторов, не контракт тарификации поставщика. TLS/certificate, отказ доступа и постоянная ошибка протокола не повторяются автоматически. Отказ до отправки возвращает типизированный `parser-market-admission/1`, `dispatched=false`; исходный резерв освобождается с подтверждением отсутствия отправки.

| Ошибка | Предметный статус | Действие до платной отправки |
|---|---|---|
| `401/403` | `provider_denied` | нулевое списание; приостановка источника до явной проверки восстановленного доступа |
| `400/422` | `invalid_request` | нулевое списание; приостановка без следующего автоматического occurrence |
| TLS/certificate | `tls` | нулевое списание; приостановка без обхода проверки сертификата |
| Некорректный JSON или структура баланса | `schema_error` | нулевое списание; приостановка до исправления контракта |
| Недостаток подтверждённой квоты | `provider_quota` | нулевое списание; ожидание штатного восстановления квоты |
| Исчерпанный подтверждённый `429` | `rate_limited` | нулевое списание; сохраняются общий cooldown и следующий допустимый срок |
| Исчерпанные временные ошибки | `unavailable` | нулевое списание; предметно отображается временная недоступность |

После durable dispatch применяется другой контракт, `parser-market-failure/1`: `stage`, `dispatched`, `paid_effect_confirmed_absent`, `original_order_only`, `requires_reconciliation`, `permanent` и типизированный `status`. Явный отказ `send-order` с HTTP `400/401/403/422` сохраняет прежний контракт подтверждённого отказа и нулевого списания. Подтверждённый `429` допускает до пяти отправок исходной попытки через общий limiter; после исчерпания попытка завершается с `rate_limited` и cooldown. Это не разрешение повторять отправку после неизвестного ответа.

TLS или ошибка схемы на этапе отправки оставляет попытку в `manual`, финансовое состояние — `dispatched`, фактическое списание — неизвестным. Потеря ответа, `5xx`, timeout/reset после отправки допускают только чтение исходного задания с той же меткой. Любая постоянная ошибка чтения, загрузки отчёта или квитанции также переводит исходную попытку в `manual`: автоматические чтения и новые отправки прекращаются, резерв сохраняется до штатной финансовой сверки. Локальный предел в 32 чтения исходной квитанции также заканчивается ручной сверкой, без новой покупки. Несовпадение метки/заказа или превышение финансового предела остаётся конфликтом, а не «нулевой стоимостью».

Корректная финансовая квитанция и корректная товарная цена — отдельные проверки. Если квитанция достоверна, а переданное поле цены повреждено, фактические единицы учитываются, предметный исход — `schema_error`. Отсутствующая цена получает `no_price`. Ручная финансовая сверка не является подтверждением цены; новая предметная проверка требует отдельного допустимого запуска после разрешения исходного расчёта.

## 4. DeepSeek: подтверждённый внешний контракт

### Выбранный протокол

[Web Tools](https://api-docs.deepseek.com/guides/web_tools/) описывает native Messages API. Запрос содержит только `deepseek_read_url`, модель `deepseek-flash`, `thinking.type=disabled`. Ссылки извлекаются из последнего пользовательского сообщения; выбор чтения делает модель. Назвать built-in через принудительный `tool_choice` нельзя. В кандидате последняя user-реплика содержит ровно один проверенный URL; название и короткая инструкция не могут добавлять вторые ссылки или явные секреты.

Доказательство чтения — согласованная пара `server_tool_use` (`read_link`) и `web_fetch_tool_result` (`kind=read_link`), связь по `tool_use_id`, успешный тип результата и непустая signature. Текст страницы клиенту не возвращается: пустое поле `data` и отображаемый URL не доказывают публичность всех redirects. Ошибка встроенного инструмента при HTTP 200 не принимается за найденную цену. Клиент не доверяет произвольному тексту модели о выполненном чтении.

### Почему MC-34 пока закрывает отправку

[Build a Chatbot, Ignored Parameters](https://api-docs.deepseek.com/guides/build_a_chatbot/#ignored-parameters) прямо различает лимит отдельного inference step и суммарный ответ раунда: `max_tokens` ограничивает шаг. Для Responses `max_tool_calls` игнорируется. В прочитанной официальной документации не найден обязательный верхний предел суммарных входных токенов, выходных токенов и количества шагов одного `deepseek_read_url` запроса.

[Тариф DeepSeek](https://api-docs.deepseek.com/quick_start/pricing/) с 18 ноября 2026 года не устанавливает отдельной платы за эти встроенные web-tools; извлечённый материал входит в модельные токены. Параметр окна контекста 1M описывает контекст модели, но сам по себе не доказывает предел суммарного расхода многошагового раунда. Следовательно, из размера отправленного JSON, одного URL, локального `max_tokens`, таймаута или 1M нельзя вывести доказанный полный денежный резерв. Расчёт обычного текстового gateway не расширяется на этот транспорт.

**Закрывающий код:** `cumulative_token_bound_unverified`. Для открытия нужен официальный жёсткий контракт совокупного расхода или эквивалентный проверяемый серверный механизм ограничения, затем реализация его в общем billing и повторная приёмка. Фиксированные суммы «на всякий случай» отсутствуют.

### Почему MC-43 пока закрывает отправку

Допуск исходного публичного домена и единственной ссылки уменьшает поверхность ошибки. Он не устанавливает свойства удалённого fetcher после redirect. Документированного механизма запрета смены host, контроля каждого redirect/IP либо полного подтверждаемого redirect chain для выбранного `deepseek_read_url` не найдено. Проверка display URL после оплаты не заменяет предоплатный контроль. Локальный fallback-fetch, самостоятельный браузер или прямой вызов с секретным ключом не подставляются вместо указанного транспорта.

**Закрывающий код:** `redirect_scope_unverified`. Требуется подтверждённое ограничение удалённого чтения и проверка его интеграции. Этот вывод не утверждает, что поставщик фактически ходит в private-сети; он фиксирует отсутствие достаточного доказательства для заданного требования.

## 5. Встроенный gateway-контракт

Единственный источник состояния — `integrations/harness-native-lab/gateway/purchase-price-read-url.mjs`. Python runtime читает его через штатный gateway, не копирует формулу предела.

| Route | Действующий operation grant | Результат |
|---|---|---|
| `GET /v1/monitoring/read-url/status` | `purchase.monitoring.status` или `purchase.monitoring` | `200`, schema/version/model/tool/thinking, `state=contract_blocked`, два blocker-кода, `safe_bound=null` |
| `POST /v1/monitoring/read-url` | только `purchase.monitoring` | в этой версии `409 contract_blocked`, `dispatched=false`, `financial_state=not_dispatched` |

Статусный grant ограничен чтением этого route и не разрешает Messages, model discovery или POST. Контекст владельца берётся из существующего resolver. После асинхронного чтения тела POST разрешение проверяется повторно. Cookie и поля actor/workspace/account из тела не участвуют в допуске. Статус не раскрывает ключи, URL, тексты или финансовые операции. Запрет действует до поиска настоящего ключа, резерва и любого обращения к провайдеру.

POST принимает только `{url, mode, name?, instruction?}`, `mode=setup|working`. Рабочий режим требует короткую инструкцию. Шаблон закрепляет JSON-схему и запрет выполнять инструкции страницы. Числовая цена не переносится в locator. Контрактные декодеры требуют полный terminal message, корректные финальные usage-поля и компактный предметный JSON; usage и encrypted signature не входят в предметную проекцию. Проверка fixture успешного ответа не меняет gate.

Лимиты сохранённого имени и locator согласованы с доменом: `name` — до 240 символов, входная `instruction` и выходная `locator_instruction` — до 600. Символы считаются по Unicode code points, как Python `len` и JSON Schema `maxLength`; данные на границе проходят без усечения, превышение отклоняется. Лимит HTTP-тела 8192 байта проверяется отдельно. Эти локальные ограничения формы и парсера не являются пределом токенов или денежного расхода поставщика и не открывают закрытый gate.

Предметный decoder различает явно подтверждённую CAPTCHA (`captcha`) и обязательный вход для показа цены (`auth_required`); в обоих случаях цена отсутствует. Эти исходы требуют той же подтверждённой пары чтения, что и остальные результаты. Ошибка инструмента при HTTP 200 сама по себе не доказывает ни CAPTCHA, ни вход. Цена передаётся только десятичной строкой: до 18 цифр целой части и 18 дробной, без преобразования в двоичное число или округления. Отрицательные значения, ноль, экспоненциальная запись и превышение границы отклоняются.

## 6. Доказательства и границы проверки

Автономно проверены штатные пути, с заменой только транспорта поставщика и, в provider unit-тестах, предметного authorization callback:

- `tests/test_purchase_price_providers.py`: три точных карточных метода, региона, SKU/размер, дробные цены, неоднозначность, изменение упаковки, исходная квитанция, отсутствие новой покупки после неизвестного ответа, отзыв разрешения, общий cooldown, скрытие финансовых job-полей прежним user-route.
- `tests/test_parser_market_service.py`: прежний сервис и wallet, legacy карточки/reviews/search, метка до 20 символов, retry/recovery/reconcile.
- `purchase-price-read-url.test.mjs` вместе с `server.test.mjs`: типизированные режимы, private/secondary URL, failed read при HTTP 200, usage, scoped grants, отзыв во время body read, нулевое число резервов и upstream dispatch при закрытом контракте, прежний Messages gateway.

Итоговые количества, исходы и точный SHA определяются общим протоколом кандидата; результаты прежней версии не переносятся на изменённые исходники. Отдельные регрессии проверяют ограниченные preflight-повторы, постоянные ошибки на каждой фазе, сохранение исходного финансового резерва и следующее: истёкший конечный lease откладывает исходное задание без освобождения/повторного резерва; явный отзыв отменяет неотправленное задание. Это не MC-45 с живыми провайдерами. Живые карточки, денежная сверка внешних квитанций, полномасштабная нагрузка и браузеры учитываются отдельными протоколами; при отсутствии результата они остаются `blocked/not run`, а не `pass`.
