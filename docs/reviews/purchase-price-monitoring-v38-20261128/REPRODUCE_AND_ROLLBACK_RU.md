Значение `c5927ce090a80cbd28cb701a7ba46a42a5f5f4ad` прочитано из `RELEASE_COMMIT`: в работающем каталоге нет Git metadata, поэтому это метка развёртывания, а не измеренный `git HEAD`. Фактические исходники и состояние службы отдельно сверены по хешам и параметрам процесса.

## Содержимое и целостность

Полный закрытый Git bundle содержит исходники, историю до исходной версии, схемы, миграции, тесты и штатные скрипты приёмки. ZIP дополняет его итоговыми отчётами, матрицами, журналами и браузерными доказательствами. Секреты, рабочие базы, provider key store и node_modules в поставку не включены.

`SHA256SUMS` проверяет содержимое комплекта. Хеш самого ZIP записан снаружи ZIP в манифесте поставки: архив не содержит самоссылочного хеша. Перед использованием следует сверить хеши, затем проверить bundle штатной командой Git:

```sh
sha256sum -c SHA256SUMS
git bundle verify purchase-price-monitoring-v38.bundle
git clone --branch implementation/purchase-price-monitoring-v38 purchase-price-monitoring-v38.bundle candidate
git -C candidate rev-parse HEAD
git -C candidate status --porcelain
```

Ожидаемый HEAD — `c33a108e036feb4487ee4f3a247abca8e1950313`, рабочее дерево чистое. Эти команды разворачивают копию исходников; они не выполняют миграции работающего сервиса.

## Окружение проверок

Используется штатный Python runtime с зафиксированными зависимостями проекта и native Harness. В выполненном прогоне использован `mcp==2.2.0`; системный Python с иной версией MCP не является равнозначной заменой. `HARNESS_DIALOG_ENGINE=native`, `HARNESS_NODE_MODULES` указывает на установленный совместимый Node runtime. Конкретные версии и хеши исполняемых файлов записаны в манифестах прогонов.

Файловые и документные сценарии требуют поддерживаемой изоляции Landlock. В локальном контейнере соответствующий системный вызов недоступен. Шесть полных модулей повторно исполняются на Alisa с Landlock ABI 4 и теми же исходниками. Изоляция не отключается ради прохождения. Исходный журнал контейнера сохраняется, а квалифицированный результат с Alisa заменяет результат целого модуля при сведении, без повторного подсчёта тестов.

Для проверки финансовой миграции используется новая копия фактических исходников текущего сервиса, а не подставленная историческая база. Копируются только кодовые файлы; рабочие БД и ключи не читаются в тестовую среду. Их перечень и хеши фиксируются отдельно.

Браузерные проверки используют реальные бинарники Chromium и Opera. Версия Opera подтверждается путём исполняемого файла, хешем и строкой User-Agent с `OPR`; Chromium не переименовывается в Opera. На Alisa используется Xvfb и обычный браузерный режим. Один worker на движок, сниженный приоритет процессов и ограничение библиотечных потоков сохраняют измеримую нагрузку стенда.

## Повторение испытаний

Команды выполняются в `candidate/products/harness-platform`. Каждый прогон пишет в отдельный новый каталог за пределами исходников. Там, где CLI предусматривает параметр, передаётся `--expected-sha c33a108e036feb4487ee4f3a247abca8e1950313`; для storage benchmark окончательная принадлежность подтверждается дополнительной проверкой HEAD и хешей в общем протоколе. Прогоны сверяют исходники до и после работы.

```sh
python acceptance/purchase_monitoring_regression.py \
  --expected-sha c33a108e036feb4487ee4f3a247abca8e1950313 --workers 4 --output /isolated/evidence/regression

python acceptance/purchase_monitoring_stress.py \
  --full --expected-sha c33a108e036feb4487ee4f3a247abca8e1950313 --duration 1800 \
  --tenants 20 --parallel 100 --duplicates 1000 --output /isolated/evidence/stress

python acceptance/purchase_monitoring_storage.py \
  --items 1000 --days 365 --samples 50 --output /isolated/evidence/storage

python acceptance/purchase_monitoring_restore.py \
  --expected-sha c33a108e036feb4487ee4f3a247abca8e1950313 --output /isolated/evidence/restore

python acceptance/purchase_monitoring_browser_audit.py \
  --root /isolated/candidate --expected-sha c33a108e036feb4487ee4f3a247abca8e1950313 \
  --output /isolated/evidence/browser-audit

python acceptance/purchase_monitoring_browser.py \
  --root /isolated/candidate/products/harness-platform \
  --expected-sha c33a108e036feb4487ee4f3a247abca8e1950313 --engine chromium \
  --audit-manifest /isolated/evidence/browser-audit/browser-inheritance-audit-c33a108.json \
  --output /isolated/evidence/chromium
```

Opera запускается отдельной аналогичной командой с `--engine opera` и новым каталогом результата. Перед фактическим запуском задаются пути соответствующих браузерных бинарников; конкретные значения сохранены в манифестах выполненных прогонов.

Точные реально исполненные команды, включая дополнения параметров и окружения, находятся в `invocation.json`, `manifest.json` и соответствующих журналах; они имеют приоритет над сокращёнными примерами выше. Отдельный штатный аудит браузерных сценариев строит полное соответствие записей загрузчика фактическим исполнениям. Сам аудит не запускает браузеры и не заявляет PASS.

Нагрузочный транспорт синтетический. Приложение, авторизация, очереди, timer, конечные допуски, финансовый резерв, квитанции, базы и история чата настоящие. Суммы тестового журнала не являются расходами у внешнего поставщика. Закрытый Read URL не подменяется успешной заглушкой. Поэтому успешные проверки трёх карточных адаптеров не закрывают обязательные испытания отсутствующего рабочего Read URL.

## Миграции и резервное копирование

Предметные таблицы создаёт штатная инициализация приложения через общий механизм миграций. Старые migration ID/checksum не переписываются. Мониторинг добавляет предмет, версии коротких правил, серии, наблюдения, уточнения и связи с существующими timer/financial attempts. Он не создаёт второй кошелёк или отдельный финансовый журнал.

Сохраняются общая identity/финансовая база, native chat и журнал отзыва ключей. Согласованная копия SQLite делается через backup API после контролируемого прекращения новой работы и сверки уже отправленных запросов. Нельзя копировать только основной файл работающей SQLite, проигнорировав WAL, либо считать удаление товара удалением его финансового аудита.

Тест восстановления создаёт новый каталог состояния. Проверяются integrity/FK, канонические хеши предметных и финансовых строк, история чата, отсутствие повторной платной отправки и возможность штатного чтения восстановленных данных. Тестовые ключи — заведомо нерабочие fixture; production provider keys в архив не копируются.

## Порядок отката

Перед будущим переключением на код без мониторинга необходимо штатно остановить выдачу новых запусков и отозвать текущие версии событий. Уже выполненный внешний эффект остаётся обязанностью общего финансового контура: исходный заказ сверяется по прежнему ID. Состояния `sent/unknown`, несверенные попытки, активные lease и неопределённая доставка блокируют переключение. Команда «Остановить» сама по себе не доказывает отсутствие внешнего расхода.

После завершения сверки нужно сохранить согласованную резервную копию и фактический актуальный журнал отзыва ключей. Старый журнал нельзя восстановить поверх нового и тем самым вновь разрешить отозванный доступ. Обратное удаление таблиц и финансовых строк не используется как способ отката.

В поставке проверены два предыдущих варианта кода на синтетическом состоянии, созданном окончательным кандидатом: полная исходная версия `6fa468e…` и фактический код текущего сервиса с меткой `c5927ce…`. Проверки включают запуск приложения/native host, чтение истории и кошелька, сохранность предметных/финансовых/timer/native строк и нулевое число внешних сетевых вызовов и новых отправок. Затем новая версия снова открывает ту же копию. Эта репетиция не переключает production и не подменяет проверку его реальной базы.

## Что требуется для снятия внешних блокеров

В собственном контуре Мастерской необходимо настроить действующий parser.market и его подтверждённые тариф/единицы/квоту. Ключи Octoport или других служб не заимствуются. После этого выполняется живая выборка минимум по три разные карточки Ozon, WB и Яндекс Маркета с независимой сверкой цены, условий и исходных квитанций.

Для DeepSeek Read URL требуется подтверждённая суммарная верхняя граница тарифицируемого многошагового запроса и проверяемое ограничение URL/редиректов/IP. Лимит отдельного inference step, таймаут, длина промпта и произвольная сумма резерва не заменяют эти свойства. Их реализация должна пройти общий grant/reserve/dispatch/usage/settlement и типизированный результат, сохранив требуемый Flash + native `deepseek_read_url` без reasoning/Search/истории основного диалога.

После открытия маршрута обязательны десять обычных товарных URL минимум на пяти доменах, сравнение первичной настройки и короткого рабочего запроса по реальным токенам и квитанциям, нагрузка на этот адаптер, все применимые ошибки каждой сетевой стадии и повторная полная приёмка нового итогового SHA. До этого результаты остаются `BLOCKED`.

Это не готовый платный адаптер, отключённый конфигурацией. В текущей версии доступны закрытый допуск и чистые функции контракта; после появления достаточных гарантий требуется завершить штатную интеграцию, финансовое согласование и перенастройку. Отдельно требуется разрешённый тестовый аккаунт для живой ветви Telegram/баланса из §14D: контрольный транспорт её не заменяет.

Выкладка в production требует отдельного разрешения владельца после рассмотрения конкретного кандидата и результатов его приёмки.
