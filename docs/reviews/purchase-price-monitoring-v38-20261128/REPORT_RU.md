# Мониторинг закупочных цен — итоговый кандидат Мастерской

**Подготовлен единый кандидат. Полная приёмка не достигнута: остаются заблокированные живые испытания и зависимая реализация платного Read URL. Production не изменён.**

Кандидат: `c33a108e036feb4487ee4f3a247abca8e1950313`. Дата отчёта: 28 ноября 2026 года, часовой пояс владельца Asia/Qyzylorda. Машинные журналы сохраняют исходные UTC timestamps.

## 1. Что поставлено

Мониторинг встроен в существующую Мастерскую. Кабинет, карточки и команды Подмастерья вызывают один типизированный реестр из 15 операций. Действуют общие авторизация, timer, устойчивые очереди, limiter, конечные допуски, резервирование монет, финансовый журнал, доставка и native история чата. Отдельного кошелька, cron или параллельной бизнес-логики чата нет.

Реализованы ввод ссылки, определение источника, название, локальный выбор неоднозначного предложения, настройка, ручная проверка, запуск, пауза, продолжение, остановка, история, график, фильтры, выгрузка и подтверждённое удаление. Расписания включают разовый момент, интервалы, дни недели и дни месяца; редактирование сохраняет несколько времён, часовой пояс и точные параметры. Критерии уведомлений сравнивают точные десятичные значения локально.

Карточные маршруты Ozon, Wildberries и Яндекс Маркета используют общий parser.market. Для однозначной структурированной цены LLM не вызывается. Неизвестный исход платной отправки сверяется по исходной операции; новый заказ не создаётся вслепую. CAPTCHA, недоступность и отсутствие цены не заменяют последнее подтверждённое наблюдение нулём. Финансовая пауза сохраняет настройки и историю, а пополнение возобновляет только задачи с соответствующей причиной без исполнения всех пропущенных сроков.

Техническая стоимость читается из единого финансового журнала только после текущей серверной проверки роли admin. Кабинет и конкретный результат в чате показывают связанные исходные попытки, единицы, токены и состояние расчёта; обычному пользователю остаются его монеты и собственные списания. Повторная проверка роли очищает административные данные и при открытой форме.

Маршрут обычных интернет-магазинов пока возвращает `contract_blocked`. Общий gateway содержит типизированный контракт и проверку допуска; отдельные чистые функции формируют setup/working и разбирают служебные блоки. Рабочего платного адаптера native Read URL пока нет: после подтверждения требуемых гарантий предстоит реализовать общий reserve/dispatch/usage/settlement и повторную настройку, затем выполнить их интеграционную приёмку. Переключатель сам по себе эту часть не включит.

## 4. Внешние блокеры и живая приёмка

В собственном хранилище ключей Мастерской parser.market не настроен. Поэтому не выполнялись реальные оплачиваемые проверки девяти обязательных карточек — по три Ozon, WB и Яндекс Маркета. Проверка конфигурации не раскрывала значения ключей. Чужие ключи и ключи Octoport не использовались.

Для DeepSeek Flash + `deepseek_read_url` не подтверждены два свойства, которые прямо требует ТЗ: доказанная суммарная верхняя граница тарифицируемого многошагового вызова и проверяемое ограничение цепочки URL/редиректов/IP. Документированный `max_tokens` относится к отдельному inference step; это не доказательство совокупного денежного предела. Наличие DeepSeek key само по себе не снимает эти ограничения. Вывод описывает отсутствие достаточного контракта для требований проекта, а не утверждает, что поставщик фактически обращается к закрытым адресам.

Закрытый допуск срабатывает до платного отправления и не резервирует произвольную сумму «на всякий случай». Контролируемые ответы поставщика в тестах не открывают этот gate. Для обычных магазинов остаются заблокированными десять обязательных URL минимум на пяти доменах, измерение реальных токенов setup/working, денежная сверка и весь относящийся к рабочему Read URL набор испытаний.

Запоздалый разрешённый ответ не должен возвращать стоимость после отзыва роли в другом виджете; это проверено отдельным сценарием с настоящими серверными ответами. Краткий [реестр локальных исправлений](gap-review.md) доступен рядом с отчётом; полные доказательства находятся в `evidence/gap-review.json` закрытого ZIP.

Предшествующие диагностические прогоны сохранены отдельно. Они помогли найти ошибки и не используются как доказательство приёмки нового SHA. Исправлены также два существовавших тестовых предположения: billing fixture теперь создаёт настоящий активный аккаунт с принадлежащим ему чатом, а проверка навигации включает новый раздел и его собственный API. Числа в этой таблице — проверки условий отдельных репетиций; они не добавляются к unit-test counts и частично проверяют одни и те же инварианты на разных этапах. Оба старых варианта кода запускались с заблокированной внешней сетью и без копирования provider keys. Текущий production не переключался. Первый запуск внешнего launcher для проверки c592 остановился до импорта кода из-за неверного имени файла репетиции; лог сохранён в `evidence/rollback-production/failed-launch/`. После исправления только внешнего launcher проверка выполнена на новой синтетической копии, исходники кандидата не менялись.

Восстановление и обратное открытие выполнялись только на синтетических изолированных копиях. Рабочая база не заменялась. Документ `REPRODUCE_AND_ROLLBACK_RU.md` описывает воспроизведение, миграции, прекращение новой работы, сверку уже отправленных операций, резервное копирование и проверенный порядок возврата к предыдущему коду. Несверенные платные попытки, активные lease и неопределённая доставка блокируют переключение.

Публикация документации не изменяет production и не объединяет draft PR в main.

Редакция отчётности r2 не меняет source SHA, код, первичные журналы или результаты тестов. Она уточняет состояние платного Read URL, формулировки MC-50 и публичные ссылки. Исходный архив проверен на Alisa: 2169 записей, 2168 контрольных сумм файлов, 228 ссылок из матрицы. Для пересобранного контейнера r2 требуется собственная проверка окончательных байтов и новый внешний `DELIVERY_MANIFEST.json`; сведения прежнего архива не подменяют эту проверку. Хеши редакционных проекций и связь с прежним архивом — в [REPORTING_REVISION.json](REPORTING_REVISION.json).

Для полной приёмки нужны собственный доступ parser.market и подтверждённый безопасный контракт Read URL, затем оставшиеся живые, финансовые, нагрузочные и интеграционные проверки на новом окончательном SHA. Пока обязательные критерии заблокированы, кандидат не объявляется полностью принятым. Выкладка возможна только по отдельному разрешению владельца.

Контракты поставщиков проверялись по официальным документам: [parser.market JSON API](https://parser.market/parser-cen-json-api/), [методы и карточки](https://parser.market/dokumentacziya/), [поля отчётов](https://parser.market/zadaniya-i-otchety/), [DeepSeek Web Tools](https://api-docs.deepseek.com/guides/web_tools/), [ограничения параметров DeepSeek](https://api-docs.deepseek.com/guides/build_a_chatbot/#ignored-parameters) и [тарификация DeepSeek](https://api-docs.deepseek.com/quick_start/pricing/). Дата повторной проверки DeepSeek: 28 ноября 2026 года. Подробное сопоставление с кодом и закрывающими условиями — [контракты поставщиков](PROVIDER_CONTRACTS_RU.md).

Факты о поведении кандидата опираются на результаты в `evidence/`, их SHA-256 в `evidence-index.json`, поимённые исходы тестов и матрицу `acceptance-matrix.json`. Пути `evidence/…` и индекс означают файлы закрытого ZIP; они не обещают открытого доступа к подробным журналам через GitHub. `SHA256SUMS` охватывает содержимое комплекта; внешний `DELIVERY_MANIFEST.json` дополнительно содержит SHA-256 самого ZIP. Диагностический запуск, статический анализ, контролируемый транспорт и живой внешний вызов обозначены раздельно.
