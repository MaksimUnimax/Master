# Матрица интеграций Мастерской — проект для согласования
28.11.2026. Не отчёт о реализации. Принцип владельца: интеграции работают так же, как существующие хозяйственные скрипты. Все расчёты, работа с API, синхронизация и обработка ошибок выполняются программно; кабинет полностью работоспособен без ИИ. Локальная матрица обслуживает однозначные команды, DeepSeek только выбирает готовый инструмент при свободной формулировке. Не создавать отдельный агент или систему шаблонов поверх Harness.
 
## Зафиксированная очередь
Live v35 c5927ce090a80cbd28cb701a7ba46a42a5f5f4ad. Подключения трёх площадок, месячная/годовая история Яндекс Маркета и сезонное планирование существуют; реальная выгрузка Маркета ещё не подтверждена. v36 — независимые коэффициенты брака возвратов и потерь сырья, 48/50 общей серверной регрессии; две проверки экспорта ожидают старые 19 листов вместо 20, требуется проверка нового контракта и браузера. Не выпускать до приёмки. Далее: отдельные локальные БД клиента по площадкам, максимально доступная количественная история, автоматическое первое заполнение и регулярное обновление, зрелый коэффициент потерь из Octoport, объединённая количественная аналитика и планирование по трём площадкам. Авито исключён. См. QUALITY_AND_MARKET_ARCHITECTURE_RU.md.

## Служебный реестр (не загружать в контекст модели)
Каждый ID — составной обработчик чтения, а не обязательно один HTTP вызов. Токен, идентификатор магазина, API host и допустимые параметры устанавливает сервер. Все записи в локальной БД; никаких изменений товаров, рекламы или цен площадки.

Основные методы Ozon/WB подтверждены чтением действующего Octoport 180660c019e5a9fa530e5ec48c9e55724a93c3ae, включая market_sources, wb_coefficients, ozon_coefficients, runtime/parameter_support. Переносить количественный адаптер и обработчик physical_outcome_union, не финансовую матрицу. Доступы, лимиты, фактическую глубину и схемы ответов повторно проверить при приёмке каждого адаптера. Для WB история детализации с 29.01.2024 по официальному руководству, но это не гарантирует наличие заказов для каждой старой когорты. Воронка хранится в непересекающихся точных интервалах, её нельзя нарезать на дни из агрегата за год. Физические возвраты отделять от cancelCount (отмены и возвраты); при отсутствии подтверждённой разбивки не применять брак возвратов ко всем потерям. Не смешивать дату события реализации и дату заказа.

## Пользовательские шаблоны (локальный реестр)
Один скрипт доступен из интерфейса, локальной матрицы и MCP. Переиспользовать существующие accounting_report, material_forecast, record_details, prepare_edit, формы и маршрутизацию; выделенные market_* инструменты — только недостающие возможности. Не дублировать уже существующие расчёты.

| ID | Описание для модели | Вход |
|---|---|---|
| market_sales | Количество заказанных, доставленных, отменённых и возвращённых изделий за период. Отдельно фактические и прогнозные чистые продажи; разрез товара/площадки/дня/месяца | from, to, source, product?, group_by |
| market_loss_rates | Коэффициенты отмен и возвратов по зрелой истории, база, покрытие, уровень SKU/категория/магазин | source, product? |
| market_sync_status | Какие магазины подключены, какой период полностью загружен, последние обновления и недостающие данные | source? |
| market_sync_request | Явно запрошенное пользователем обновление или заполнение отсутствующих периодов. Только постановка задания в очередь, без произвольных HTTP вызовов | source, from?, to? |
| accounting_report (расширение) | Фактический расход сырья, эквивалент по реализованным изделиям, нормативная и плановая себестоимость, имеющиеся остатки | view, start, end, product/material при поддержке фильтра |
| material_forecast (расширение) | Сколько изготовить и закупить на основании продаж выбранного исторического периода, актуальных рецептур, запасов и двух коэффициентов брака | source, history_from, history_to, target_from, growth, reserve, lead, include_wip |
| record_details / prepare_edit | Читать/менять два коэффициента брака, рецептуры, материалы через существующий механизм разрешений | существующие схемы |
| catalog mapping (штатный обработчик) | Просмотр несвязанных SKU и явная привязка к изделию; не угадывать | source, SKU, product ID |

Одна и та же проекция должна обслуживать общий источник "все подтверждённые магазины" без двойного учёта ручных проводок. Объём вывода ограничивать, но итог рассчитывать по всему набору. Не передавать в модель сырые страницы заказов или ключи. Пример market_sales: {"from":"2026-05-01","to":"2026-05-31","source":"all_marketplaces","group_by":"product"}; ответ содержит статус, даты, покрытие, количество по каждому товару, факт и оценку отдельно. Источник и SKU разрешаются в текущей области владельца.

## Общий исполнитель
Декларация: ID, версия, краткое назначение (для пользовательского инструмента), input/output schema, required scope, effect, handler, источник и ограничения. Служебный реестр содержит реальные HTTP методы/схемы, правила дат, пагинации, нормализации, deduplication. LLM получает только публичные описания инструментов, а не весь registry. При первой успешной привязке — durable backfill максимально доступной истории; суточное обновление незрелых окон и поздних возвратов, каталог по необходимости. Хранить состояние задачи/lease, курсор, ID отчёта, дату наблюдения, окно покрытия, хеш/версию схемы. Не привязывать сбор к открытой вкладке. Период/магазин/ключ валидируются сервером. Не загружать повторно подтверждённые старые окна, если нет причины обновления.
 
429 — Retry-After / правила API, durable отложенный повтор; 401/403 — остановить источник, показать недостающий доступ; временные 5xx/таймаут — ограниченные повторы чтения; неоднозначная генерация отчёта — сверить ID/статус, без слепого нового заказа; неизвестная схема, повтор курсора или отсутствующая страница — incomplete, не выдавать нули; ошибка одного источника не уничтожает сохранённые данные. Ответы: ready, collecting, partial, denied, error, no_data_confirmed. Не смешивать неподтверждённый ноль и настоящий ноль. Каждый handler имеет тесты схемы, полноты, повторов, 429, изоляции, смены ключа и сверку реальных количеств с кабинетом. Сбор/вычисление не обращаются к DeepSeek. Монеты за модель только если она действительно была вызвана для свободной команды.

## Обязательное правило владельца от 28.11.2026 — два способа управления

Применять [CORE-DUAL-01](CORE_DUAL_CONTROL_RU.md) к каждому шаблону пользовательского реестра. Кабинет без модели вызывает тот же скрипт, что чат через локальную матрицу или инструмент. Подключение, сбор истории, статус, остановка/возобновление, коэффициенты, сопоставление SKU, отчёты и план закупок доступны из обоих каналов. Внутренние API-операции остаются за общим исполнителем; ключи вводятся в защищённое поле и не передаются модели. Не создавать UI-only или chat-only бизнес-операции и второй планировщик.
