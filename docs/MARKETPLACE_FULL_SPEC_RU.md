## 2. Паспорт каждого шаблона

Обязательна машиночитаемая декларация, валидируемая при запуске и CI. Не текстовая заглушка, а зарегистрированный вызываемый обработчик.

Поля:
- stable_id, version, kind (internal_api/user_operation), краткое назначение, handler, input_schema, output_schema, required_scope, role, effect, store_binding, ссылки на источник/дату проверки.
- Пользовательский шаблон: краткое русское описание для модели, типизированные обязательные/необязательные параметры, defaults; привязки к UI, локальной матрице и MCP. Не загружать всю служебную API-матрицу в модель.
- Служебный шаблон: фиксированный разрешённый origin, HTTP-метод/путь, доступы, схема ответа, период/часовой пояс/глубина истории, пагинация и терминальное условие, нормализация и ключи дедупликации, минимальный набор сохраняемых полей, проверка покрытия, класс квоты и область совместного лимита, timeout.
- error_policy: явное сопоставление применимых HTTP/транспортных/доменных ошибок с состоянием, действием, допустимостью и бюджетом повтора, профилем задержки; общий профиль плюс обоснованные исключения метода. Неизвестная ошибка имеет fail-closed fallback. Каждый применимый случай связан с тестом.
- progress_policy: job_id, идемпотентность, checkpoint, lease/fencing, отмена/возобновление, неизвестный результат, сохранение последнего подтверждённого снимка, условия публикации полного результата. Асинхронный отчёт — generate/poll/download/validate/publish, сохранённый report_id, срок действия и безопасное восстановление.
- tests: template_id/version → сценарий → ожидаемый результат → доказательство фактического исполнения. N/A допускается только с объяснением, почему ветвь невозможна для метода. Для локального шаблона 429 внешней площадки проверяется как состояние фоновой синхронизации; не добавлять HTTP-вызов в локальный расчёт ради теста.

Сервер сам разрешает область владельца, подтверждённый магазин, токен и версию подключения. Модель не передаёт URL, заголовки авторизации, SQL, произвольный путь к БД. Пользовательский контракт не дублируется для чата. UI вызывает тот же код напрямую; локальная матрица обслуживает однозначные команды, DeepSeek только выбирает пользовательский инструмент и передаёт параметры при свободной формулировке.

## 3. HTTP 429 — штатное состояние, не исключение работы

**Общий ограничитель:** до HTTP-вызова атомарно получить разрешение; учитывать фактические документированные квоты поставщика на продавца/кабинет, токен, группу методов, общий лимит сервиса, если применимы. Несколько ключей одного продавца, worker-процессов, чатов, браузеров, пользовательских/автоматических задач не создают независимые квоты для обхода. Разделять области квот, чтобы один ограниченный магазин не блокировал остальных. При неподтверждённой квоте — консервативный режим до проверки, не безлимитный.

**Реакция:** прочитать и проверить Retry-After (секунды или HTTP-date), документированные заголовки reset/retry и ограничения метода. Следующая попытка не раньше наиболее строгого подтверждённого срока из официального минимального интервала, серверного указания и ограниченного backoff. Jitter только неотрицательный. При отсутствии, просрочке или ошибочном заголовке использовать документированный интервал и консервативный экспоненциальный backoff. Время ожидания не сокращается до таймаута модели. Не использовать единый фиксированный интервал для всех API. Профили и их подтверждения версионировать.

**Устойчивость:** сохранить rate_limited/waiting_retry, next_retry_at, область cooldown, job_id, checkpoint, report_id, число попыток и безопасную причину. Освободить рабочий слот; ждать в устойчивой очереди, а не держать процесс/запрос/диалог. При перезапуске восстановить cooldown и состояние; не начинать отчёт или страницы заново. Перед каждым вызовом проверить разрешение, поколение подключения, состояние задачи и lease. Ручной запуск/смена канала не обходит cooldown. Если известен report_id, не создавать отчёт повторно.

**Серия 429:** конечный бюджет активных попыток и длительности цикла по профилю; после исчерпания — durable deferred/waiting_for_provider/needs_attention с безопасной следующей проверкой или явным продолжением после допустимого срока. Не бросать данные и не объявлять успех, не устраивать бесконечный быстрый цикл. Для обычных временных сбоев применять штатную политику Octoport (до 5 повторов с базовой задержкой 8 секунд как исходная настройка там, где допустимо), но требования конкретного API, Retry-After, backoff, семантика повторяемости и безопасный лимит имеют приоритет.

**Интерфейс и чат:** одинаковый понятный статус, например «Площадка ограничила частоту запросов. Следующая попытка не ранее 14:35. Уже получено 8 периодов из 12». Если знаменатель неизвестен, не придумывать. Показывать последнее успешное обновление и фактическое покрытие, дать остановить и продолжить. Остановка запрещает новые запросы; уже отправленный запрос безопасно завершить/сверить. Не просить ИИ принимать решение о каждом повторе.

429 не считается обработанным, если приложение вернуло пустой результат как успех, потеряло checkpoint, запросило второй отчёт, повторило раньше срока или оборвало весь сбор.

## 4. Обязательная таблица остальных ошибок

| Событие | Действие общего исполнителя |
|---|---|
| 400/422, неверный параметр | Не повторять неизменённый запрос; типизированная диагностика. Деление периода только по подтверждённому контракту. |
| 401/403, отозванный/недостаточный ключ | Остановить затронутый источник до проверенного восстановления доступа; не обходить права, не повторять тем же запрещённым ключом. Не стирать старые снимки, не выдавать их как свежие. |
| 404/410 | Различать отсутствие сущности, устаревший endpoint и истёкший отчёт. Не принимать за нулевые продажи без подтверждения семантики. |
| 409, конфликт | Сверить ID, поколение ключа, lease и состояние, исключить дублирование. |
| 408/500/502/503/504, timeout/reset/временный DNS | Ограниченные безопасные повторы чтения, backoff+jitter, уважать Retry-After. При исчерпании — deferred/needs_attention, не падение. |
| TLS, неверный сертификат/origin | Блокировать, не отключать TLS, не передавать секреты по редиректу, не повторять бесконечно. |
| HTTP 200 с ошибкой JSON/неизвестной схемой | Проверить доменный статус и обязательные поля; не подтверждать полноту. |
| Повтор/пропуск страницы, курсор, изменение total | Не объявлять полноту; повтор по контракту, отметить недостающие окна; не удваивать строки. |
| Отчёт PENDING/PROCESSING | Сохранить ID, отложенный poll; не держать рабочий слот. |
| Неизвестный исход generate | Не генерировать повторно вслепую. Сверить доступными официальными методами/ID; иначе uncertain и разрешённое восстановление. POST чтения и генерация отчёта имеют разные профили идемпотентности. |
| Повреждённый/неполный ZIP/CSV/XLSX, превышение лимита | Ограничить скачивание/распаковку, не исполнять вложения, не публиковать неполный отчёт; безопасный повтор только при допустимости. |
| БД занята/недоступна, disk full, crash | Не подтверждать до commit; устойчивый идемпотентный receipt/checkpoint, fencing и сверка; сохранность прежнего снимка. |
| Смена ключа, удаление/архив/отмена | Инвалидировать старый допуск и lease; не смешивать магазины и поколения; возобновлять только в разрешённой области. |

Единые типизированные состояния как минимум ready, collecting, waiting_retry, partial, denied, uncertain, needs_attention, stopped и подтверждённый zero/no_data. Неполный результат не подменяет последний полный снимок. Хранить проверенные страницы, подтверждение полноты, версию схемы и дату наблюдения. При разных физических БД нужен согласованный идемпотентный commit/receipt и проверяемое восстановление между ними. Возврат 0 только при подтверждённом отсутствии данных. Логи/ошибки не содержат ключей, персональных данных покупателей, подписанных ссылок и внутренних stack trace в клиентском ответе. Ошибка одного метода не ломает весь сервис.

## 5. Локальная история, коэффициенты и производственное ядро

Схема по аналогии с market_data.local/path_for: физически разделённые файлы по клиенту/площадке, магазин внутри подтверждённой области, уникальные IDs и поколения подключения. Только серверные разрешённые запросы. База содержит каталог/SKU/offer_id, категории, количественные факты, даты/статусы, естественные идентификаторы, coverage, версию и квитанции синхронизации. Сохранить ранее собранные данные и ключи; безопасно мигрировать существующие YM-снимки и сопоставления без задвоения. Календарные отчёты и когорты заказов не взаимозаменяемы. Если по старому периоду доступны только агрегаты реализации, хранить их как таковые, не выдумывать даты заказов и число отмен. Не делать автоматических хозяйственных проводок от исторического импорта. При дублировании источников не суммировать одни продажи повторно.

В проверенных зрелых когортах по 365-дневному периоду рассчитывать order_loss_rate = уникальные потерянные единицы / исходно заказанные единицы; базовый метод WB из Octoport (cancelCount/orderCount) не считать доказательством количества физических возвратов. По Ozon переиспользовать physical_outcome_union; YM — адаптер на подтверждённых полях. SKU, при недостатке доказанной истории категория, затем магазин; установить и документировать объективный критерий достаточности выборки и покрытия, протестировать fallback. Не выдумывать проценты. Выводить числитель, знаменатель, источник и интервал. Заказы моложе 30 дней или с незавершённым статусом — оценка, не факт. Ожидаемые итоговые потери от исходного объёма не меньше уже известных потерь; не вычитать коэффициент второй раз из очищенных продаж. Уточнять поздние возвраты по исходной когорте. Отдельно хранить/оценивать физические возвраты; если разбивка не подтверждена, не умножать коэффициент брака на все отмены/невыкупы.

Два пользовательских коэффициента v36 сохраняются независимо (NULL — не задан, в прогнозе добавочные потери не учитываются). Брак возвратов относится только к физическим возвратам; годные считаются пригодными к повторной продаже. Не добавлять второй виртуальный приход. Производственный брак — доля потерянного сырья от общего расхода; полезная норма / (1 − доля потерь). Отдельные показатели фактического расхода и планового расхода, нормативной и плановой материальной себестоимости. Контроль: 100 доставлено, 20 физически возвращено, 25% брака возвратов, 10% потерь производства, 9 ед. на изделие => 80 чистых продаж, 85 изделий к обеспечению до вычета готового запаса, 765 ед. полезной нормы, 850 ед. общего расхода. Без заданных коэффициентов — 80 изделий, 720 ед. материала. Рецептуры, фактические складские движения и историческая себестоимость не переписываются. Сезонный план по месяцу/году, рост, упаковки, страховка, текущие остатки и перенос между месяцами. Объединённые данные всех площадок и явное сопоставление SKU с изделиями; неизвестные связи видны, не молча исключаются.

## 6. Обязательные испытания

**A. Контрактные и расчётные тесты.** Все 18 служебных шаблонов и все пользовательские операции, применимые ветви error_policy, реальные очищенные форматы ответов, границы дат/квот, роли, схема, пропущенные поля, пустые ответы, pagination, единицы, дедупликация, коэффициенты, прогноз, экспорт. Проверять фактическое состояние БД и точные количества, а не только HTTP 200. Детерминированные часы для длительных задержек.

**B. Интеграционные fault injection.** Воспроизводимый HTTP-стенд/официальная песочница с управляемым лимитером. Использовать настоящий общий исполнитель, нормализацию, очередь, БД и обработчик 429, не подменять их моками. Для каждого сетевого шаблона и каждого применимого этапа (включая poll/download) прогнать: обычный успех; 429 на первом/промежуточном запросе, не менее трёх подряд, затем успех; постоянный 429; Retry-After секунды/дата/некорректное значение/нет заголовка; временные 5xx/timeout; 401/403 без повторов; ошибка схемы; подтверждённый ноль. Отдельно проверить crash до/после checkpoint, неизвестный исход создания отчёта, рестарт в cooldown, гонку двух workers, истечение lease, смену ключа, отмену при ожидании. Локальные операции: повторное чтение без HTTP, stale/partial/zero, модель отключена, баланс ноль, состояние фонового задания одинаково в обоих каналах.

**C. Стресс-тесты на изолированном стенде.** Предлагаемые минимальные уровни приёмки; их увеличение по фактической нагрузке допускается, уменьшение только по согласованию с владельцем:
- 100 параллельных клиентских запросов, 1000 запусков одного окна из разных каналов. Одна логическая задача; ни одного задвоенного события; после готовности локальные чтения не вызывают API.
- ≥1000 событий тестового HTTP-транспорта на адаптер с регулируемым порогом и гарантированным 429, серийными/постоянными/случайными отказами. Детерминированные часы допустимы, отдельно прогнать реальные интервалы времени. Замерить фактические исходящие попытки, а не только вызовы UI.
- ≥20 изолированных тестовых клиентов/магазинов, все три площадки, несколько ключей одного продавца, параллельный backfill и ежедневный сбор. Общий лимит одного продавца, независимость других областей.
- ≥30 минут смешанного непрерывного прогона с 429/5xx, рестартами, отменами, повторными командами. Фиксировать p50/p95/p99/max, throughput, CPU/RAM, открытые соединения, глубину очереди, число 429, retry, дедупликаций, время восстановления и целостность БД. До прогона зафиксировать мощность стенда, измерить baseline, определить конкретные ресурсные/latency пределы, не завышать после получения результатов; при превышении — блокер и оптимизация. Ноль ранних повторов, неконтролируемых падений, дублей, утечек и ложных полнот.

**D. Живые проверки.** Каждый обязательный доступный метод трёх площадок проверить на авторизованных выделенных магазинах, с минимально достаточным объёмом read-only запросов. Проверить актуальную глубину истории, реальный формат/пагинацию, количественную сверку по датам/SKU с кабинетом. Без искусственной перегрузки чужого API, обхода квот и лишних ключей. Если естественно возникает 429, сохранить очищенные квитанции, timestamp и показать возобновление без дублей. Если не возник — честно указать, а гарантированные сценарии 429 доказать на стенде. Нет доступа/данных — явно BLOCKED для живого сценария, не PASS. Не менять ассортимент/цены/рекламу/остатки площадок; не копировать ключи в тестовые логи или архивы.

**E. E2E и регрессия.** Полный пользовательский цикл обеими поверхностями: подключение и защищённый ключ, первичный импорт, 429, статус, восстановление, остановка из другого канала, привязка SKU, отчёт, изменение двух коэффициентов, расчёт закупок, экспорт. Кабинет без DeepSeek/монет, чат без перехода к кабинету, оба вызывают один handler. Измерить вызовы DeepSeek и модельные списания: скрипты, автоматический сбор, retry и UI — ноль. Свободная формулировка — только штатная тарификация фактического вызова модели. Chromium и Opera, весь актуальный серверный/JS/browser regression, миграции на безопасной копии, restore и проверка совместимости. Не удалять старые тесты, не ослаблять assertions, не считать тесты заглушек доказательством живой работоспособности.

## 8. Поставка и выпуск

Один итоговый кандидат на актуальной рабочей базе, не последовательность промежуточных прод-релизов. Исходники, точный base/candidate SHA, полный manifest с SHA256, миграции, тесты, README запуска, матрица MP-T01–40 и DUAL-01–08, журнал стресс-тестов, сверка реальных данных, отчёт расходов, инструкция backup/restore/rollback; один комплект доказательств в GitHub и единый ZIP/Git bundle в разрешённом контуре. Секреты и закрытые исходники не публиковать в неподходящий репозиторий. Учитывать параллельную работу других агентов: не затереть main/новые релизы, без force-push, согласованный deploy lock. Не переключать production до полной приёмки и действующего разрешения владельца на выкладку. Если его нет, закончить одним готовым к выпуску кандидатом, не просить согласований на каждую часть. При разрешённой выкладке — актуальный SHA, резервная копия кода и всех затронутых БД, проверка миграций, smoke действующего сайта, сохранность подключений/данных, наблюдение и штатный откат при критическом сбое. Octoport не изменять.

Итоговый отчёт: что реализовано, точные ссылки/хеши, фактические числа тестов, покрытие по шаблонам, метрики нагрузки и 429, расходы, сохранность данных, перечень неподтверждённых/заблокированных критериев. Не выдавать подготовленную документацию, тестовую имитацию или частичный кандидат за работающий production.
