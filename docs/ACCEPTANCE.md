# Этапы и обязательная приёмка
Статус: документы, а не готовый сервис. По команде владельца: (A) завершить S01–S14, все OPEN отметить тестом или блокером; (B) изучить актуальный Harness и выбрать reuse; (C) спроектировать и реализовать точное расчётное ядро/схему БД; (D) постранично поднять весь базовый интерфейс и операции, подключить интеграции и помощника с общей матрицей; (E) независимые тесты, ручная приёмка и затем допуск к развёртыванию. Порядок разработки предложен, не является разрешением на прод.

## Обязательный фундамент первой рабочей версии (уточнение владельца)
Не откладывать ИИ до появления трафика или полного функционального паритета. При проектировании ядра сразу определить контракт операции, каталог/матрицу, локальный фильтр, FAQ, адаптер DeepSeek, общий исполнитель и типизированные UI-действия. Первый вертикальный срез должен демонстрировать сквозную работу помощника: понять свободную формулировку, запросить недостающее, вызвать проверенную функцию, сохранить данные, обновить форму/страницу и сообщить результат. Проверить тот же сценарий вручную и через шаблон без LLM; одинаковые данные и результаты. Измерять вызовы и стоимость с первого релиза. Каждая последующая функция добавляется одновременно в ручной интерфейс, каталог операций, матрицу/справку и приёмочные тесты. Отраслевые расширения подключаются к этому же контракту, не создают собственный агент. Полноценный автономный Harness, универсальный runtime плагинов и большой чат не являются условиями первого среза. Окончательный выбор переиспользуемых компонентов — после аудита Octoport. SEO запускается параллельно, не является условием включения ИИ.

Для каждого фактического элемента конкурента и каждого расширения: stable ID → UI → handler → схема → матрица/FAQ → тесты → результат. Проверки: CRUD/архив/исправления; отсутствие двойных проводок; разделение прибыли и cashflow; исторические партии; единицы/пачки; возврат и отмена; разные источники с одинаковыми ID; повтор и параллельность; изоляция мастерских и права; недоступность API и ИИ; импорт и экспорт; пустые значения/неизвестные/округления; контекст страницы, фильтры, формы, подсветка; mobile layout; отсутствие ключей в логах; восстановление после сбоя. 
Контрольные числа: S01 300/700/70%/400; S03 23600/8914/14686/9986/10800; S14 повтор заказа 3000 → ровно одна продажа, COGS +1222, прибыль +1778; бусины 400/40 → 10, 800/400×40=80. Дополнительный сценарий 120 изделий, 680 остаток → 11 пачек на 30 дней при заданных допущениях. Сверять каждую проводку и остаток.

Отдельный корпус запросов: FAQ (включая длинные сложные объяснения), UI, read, write, многооперационные, опечатки, неоднозначность, отрицательные примеры, провайдерские сбои. Замерять корректность маршрута, параметры, false positive, долю zero-LLM, стоимость, p95. Ошибка распознавания не должна изменять данные. Все вычисления независимо от LLM. Продукт не допускать по одним happy-path тестам.
