# Мастерская v31: воспроизводимая поставка и будущий выпуск

## Область документа

Это инструкция для полного проверенного дерева Мастерской. Она не изменяет
работающий сервис сама по себе. Не использовать старые Octoport unit-файлы
или старые скрипты `foundation/prepare.py` для сборки этого кандидата.
Исходники берутся из одного commit полного Git-дерева либо из его Git bundle.
Публичная авторская выборка без закрытых зависимостей недостаточна для запуска.

Сопутствующие `release.json`, `checksums.sha256` и `source-manifest.json`
описывают commit, upstream, runtime digest и содержимое конкретного архива.
Git delta приложена для ревью; установка выполняется из полного дерева,
а не применением дельты к работающему каталогу.

## Подготовка окружения

1. Распаковать архив в новый каталог, проверить SHA256 файлов и
   `git bundle verify` для вложенного bundle. Сверить checkout commit с
   `release.json`; исключить незакоммиченные runtime-изменения.
2. Использовать Linux x86_64 с поддержкой Landlock, Python 3.12 и
   совместимым Node. Создать отдельный Python venv. Из каталога
   `products/harness-platform` установить `requirements.txt` вместе с
   закреплённым `constraints-linux-py312.txt`. При использовании готового
   runtime сверить версии, особенно библиотеки документов и медиа.
3. В отдельном Node runtime выполнить `npm ci` по
   `deploy/runtime/package.json` и `package-lock.json`. Путь
   `HARNESS_NODE_MODULES` должен указывать на полученный `node_modules`.
   Нельзя подменять lockfile произвольным последним Harness.
4. Для полной browser-приёмки установить Playwright и настоящие Chromium
   и Opera в отдельный test runtime. Версии, executable digest и user agent
   должны быть записаны в evidence. Браузеры не нужны серверу в production.
   Принятая Opera запускается с `--headed` на Xvfb: её headless CDP wheel
   не прокручивает даже независимый минимальный HTML. Это настройка режима
   настоящего браузера; тесты и критерии остаются прежними.
5. Выполнить полный Python, native и оба browser runner. Fixture-набор
   запускается без production keys, production DB и внешних отправок.
   Явно задать `HARNESS_DIALOG_ENGINE=native`: без этой переменной launcher
   может выбрать прежнюю legacy-ветку. Временные каталоги разных прогонов
   должны различаться; для UNIX sockets использовать короткий TMPDIR.
   Для теста обновления рядом с корнем исходников должен находиться
   `baseline/products/harness-platform` из snapshot commit
   `02a2efdbbe716fcf642ebf9aaf12f30ddea6476f`. ZIP содержит этот вход;
   при Git checkout он создаётся через `git worktree add`, как описано в README.

## Конфигурация продукта

| Настройка | Контракт |
| --- | --- |
| WorkingDirectory | `RELEASE/products/harness-platform` из одного commit |
| Точка входа | `python -m platform_core.podmasterye_serve --state STATE --port PORT` |
| Сеть приложения | Loopback `127.0.0.1`; существующий reverse proxy настраивается отдельно |
| `STATE/stage.sqlite3` | Прежняя база Мастерской; не база Octoport |
| `STATE/chats` | Прежние chat journals и связанные файлы; сохранить владельцев и права |
| `STATE/provider-keys` | Собственные DS/OR credentials, доступные серверу; содержимое не журналируется |
| `STATE/telegram.json` | Собственная конфигурация Telegram, единая для возможностей аккаунта |
| `HARNESS_NODE_MODULES` | Закреплённый отдельный Node runtime |
| `HARNESS_DIALOG_ENGINE=native` | Штатный durable native engine |
| `PODMASTERYE_PUBLIC_ORIGIN` | Общий строго проверяемый HTTPS origin; целевой адрес `https://mastersckaya.ru` |
| `PODMASTERYE_INDEX_PUBLIC` | Остаётся `0` до отдельной публичной приёмки |
| `HARNESS_WEB_ENABLED` | Включать согласно принятому состоянию Search/Fetch и финансовой конфигурации |
| `HARNESS_OPENROUTER_ENABLED` | Требует собственного ключа, тарифов и допуска совместимых моделей |
| `OPENROUTER_PROXY_URL` | Требуемый для OR доверенный server proxy endpoint; отсутствие корректного маршрута закрывает OR. Не задавать произвольный URL из пользовательского запроса |
| `YOOKASSA_PAYMENTS_ENABLED` | Остаётся `0` до отдельной боевой платёжной приёмки |

Сохраняются существующие защищённые настройки почты, платёжного магазина,
Telegram и шифрования интеграций. Не переносить их из Octoport и не включать
секреты в новый файл исходников. Не переименовывать прежние DB, cookie и
внутренние идентификаторы ради внешнего бренда. Полный реальный environment
проверяется у действующего service перед будущей выкладкой; этот документ
не является заменой его конфигурации.

## Согласованная резервная копия

Перед переключением запретить новые изменения согласно эксплуатационной
процедуре и остановить текущий процесс Мастерской вместе с его фоновыми
операциями. Снять одну согласованную точку: основной SQLite, все отдельные
native DB/journals, attachments и authored files, конфигурация интеграций и
ключи шифрования. Секретная резервная копия остаётся закрытой на сервере.

Копирование одного SQLite-файла во время активной WAL-записи не считается
достаточной резервной копией. Для онлайн-копии использовать SQLite backup
API; финальная точка всех ресурсов требует согласованной паузы. Записать
SHA256, владельцев, режимы файлов, исходный release и зависимости. Проверить
`integrity_check`, `foreign_key_check`, количества существующих объектов,
exact wallet/held и возможность открытия native истории.

Репетиция текущего переноса уже использует readonly backup действующей
Мастерской, обезличивание на копии и проверку restore. Её объём и ограничения
описаны в `TRANSFER_MIGRATIONS_RU.md` и evidence; она не заменяет новую
резервную копию непосредственно перед будущим переключением.

## Единое переключение

1. Ещё раз сверить текущий production release Мастерской и применимые
   изменения общего ядра с зафиксированными входами кандидата. Новый
   неподхваченный runtime diff требует интеграции и повторной приёмки.
2. Подготовить новый immutable release directory и отдельный runtime.
   Проверить всех владельцев путей, доступ к собственным key files и
   возможность чтения файлов/журналов существующего аккаунта.
3. После согласованного backup переключить существующий service на весь
   новый release. Не запускать два релиза на одном writable state.
4. Штатный startup применяет версии миграций с checksum и SAVEPOINT.
   Проверить список receipts, FK/integrity, пользователей и текущие
   exact balances/reserves. Незавершённые provider attempts сохранить.
5. Проверить login, обязательную защиту администратора, один основной чат,
   файл и документ, локальный калькулятор, учётный отчёт, кошелёк,
   экран сверки, расписание и восстановление. Внешние отправки и платные
   операции выполнять только в принятом отдельном контуре допуска.
6. Открывать трафик после проверки. Не использовать этот выпуск как повод
   менять DNS, Nginx, TLS, SMTP, секреты другого продукта или включать
   платежи, необратимое удаление и неподтверждённые модели.

## Откат

Остановить новый service, сохранить его диагностический state без очистки
unknown attempts. Восстановить согласованную точку **всех** данных и прежний
исходный release/runtime. Нельзя просто вернуть старые Python-файлы поверх
новой схемы или восстановить только кошелёк, оставив новую историю/файлы.

Повторить проверку FK/integrity, количества объектов, балансов, held,
активных сеансов, истории, файлов и обработки незавершённых попыток.
Убедиться, что работает только один процесс продукта. Если после точки
backup уже были реальные внешние операции, их сначала сверяют по receipts;
restore не отменяет списание у поставщика и не разрешает повторять вызов.

## Разделение факта и плана

Прогон кандидата на Alisa, репетиция миграций и ограниченная isolated live
приёмка описываются своими evidence. Production deploy, новый домен,
боевой платёж, доставка реального сообщения адресату и политика удаления
имеют отдельные условия и не получают статус PASS из тестового прогона.
