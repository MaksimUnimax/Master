# Мастерская v31: миграции, сохранность и откат

## Исходное и целевое состояние

Миграция расширяет действующую SQLite-базу аккаунтов/учёта. Native chat journal,
файлы и каталоги конфигурации остаются отдельными ресурсами прежнего runtime.
Аккаунты, основной чат, материалы, рецептуры, движения, покупки, продажи,
настройки, grants и попытки поставщиков не получают новые случайные бизнес-ID.

| Существующая сущность | Изменение |
| --- | --- |
| `identity_accounts`, `identity_sessions` | Прежний вход и токены; отдельные metadata сеанса с реальным/неизвестным временем |
| `coin_*`, `usage_*` | Сохраняются целые суммы, резервы и исходные квитанции; добавляются индексы и audit сверки |
| `pm_*` | Хозяйственные записи и FK сохраняются; v30 настройки разрешений проходят общий registry миграций |
| `timer_events`, `timer_runs` | Additive поля domain, leases, attempts, result/manual и статусы доставки |
| `timer_drafts` | Прежний draft/receipt механизм; workshop binding и срок предпросмотра |
| `octopus_preferences` | Та же таблица общения, без копии под новым названием продукта |
| `illustrations` и связанные таблицы | Добавлена версия/fingerprint; существующие изображения не заменяются |
| `platform_schema_migrations` | Единый журнал version/checksum/applied_at |

| `20261127_finance_payments_v1` | Audit административной сверки существующих checkout |
| `20261127_lifecycle_v1` | Обратимый lifecycle, revision, audit запросов, паузы интеграций |

| `20261127_permissions_v30` | Сохранённые v30 права помощника и их общий migration receipt |
| `20261127_timer_engine_v1` | Additive upgrade существующего durable timer engine |
| `20261127_workshop_timer_v1` | Встроенная composition, bindings, сроки и request receipts |
| `20261127_timer_admin_v1` | Audit административной паузы |

Фактический список и checksum читаются из `/api/admin/system` или
`schema_migrations.applied(db)`. Нельзя изменять тело уже применённой версии:
несовпадение checksum останавливает обновление. Следующее изменение схемы
получает новый ID миграции.

Каждая версия выполняется в SAVEPOINT вместе со своей записью журнала.
Использование `executescript`, неявно завершающего внешнюю транзакцию, исключено.
Ошибка DDL/upgrade/FK откатывает эту версию; принятые ранее версии остаются
завершёнными, а повтор старта безопасно продолжает upgrade. Для отката всего
выпуска служит согласованная резервная копия, а не удаление новых таблиц
непроверенным down-script.

## Репетиция на реальной обезличенной копии

Исходная рабочая база прочитана на Alisa через readonly SQLite backup.
До и после резервирования проверяются SHA256 исходных файлов. Никакая raw
production-копия, токен, ключ, контакт или содержимое чата не включаются в
релизный ZIP. Обезличивание выполняется только на копии; сохраняются technical
IDs, FK, количество записей и точные финансовые поля. После замены содержимого
используются secure_delete/VACUUM и отдельная проверка остаточных значений.

Объём этой рабочей базы ограничен: в момент копирования хозяйственных записей
материалов/продукции/движений не было. Поэтому реальная копия доказывает upgrade
существующих аккаунтов, денежных операций и истории, а сохранность заполненного
хозяйственного учёта дополнительно проверяется на наполненных сценариях
текущей регрессионной матрицы. Отсутствующие business rows не выдаются за
проверенные production-данные.

В rehearsal сравниваются исходные столбцы старых таблиц, количество объектов,
exact суммы и held, FK/integrity, native история/файлы, повтор запуска и restore.
Доказательства конкретного прогона включены в отчёт приёмки; синтетическая
fixture и фактическая production-copy проверка там разделены.

Отдельно сохранена полная закрытая копия собственных данных и конфигурации
Мастерской с проверкой восстановления файлов и четырёх SQLite. Состав,
согласованность снимка и процедура восстановления описаны в
[инструкции резервного копирования](../products/harness-platform/docs/MASTER_BACKUP_RESTORE_RU.md).
Raw backup остаётся только на сервере; в поставке содержится безопасная metadata.

## Порядок будущего развёртывания

1. Зафиксировать commit и проверить source manifest поставки. Поставить Python
   зависимости и Node из lockfile в отдельный runtime; выполнить полную
   активную тестовую матрицу этой версии.
2. Проверить текущие настройки собственного продукта: state, public origin,
   provider key directory, Telegram, почта, ЮKassa и Метрика. Значения секретов
   не выводить в журнал. Не заимствовать конфигурацию Octoport.
3. Перед переключением остановить новые пользовательские изменения и фоновые
   операции по принятой эксплуатационной процедуре. Сохранить все связанные
   DB/native journal/file store/config одной согласованной точкой, права и
   контрольные суммы; проверить чтение backup.
4. Создать отдельный release directory из точного commit. Не исправлять файлы
   внутри работающего release и не заменять current по частям.
5. Запустить приложение с существующим state. Версионируемые миграции
   выполняются через штатный lifespan/Store. Проверить integrity/FK,
   reconciliation invariants, один основной чат, login/admin и локальные отчёты.
6. Выполнить ограниченный smoke без включения неподтверждённых платежей,
   удаления, рассылок или индексации. Сверить wallets/reserves и ошибки после
   старта. Только затем открыть пользовательский трафик.
7. При отказе остановить новый процесс, сохранить диагностическую копию,
   восстановить **полную** согласованную точку данных и прежний release/runtime.
   Перед открытием трафика проверить те же invariants. Не запускать два разных
   релиза на одном writable state параллельно.

Этот документ описывает процедуру будущего выпуска. Рабочий Octoport, DNS,
Nginx, SSL, почта и активный service Мастерской переносом кода не изменяются.
Включение боевой оплаты и необратимого удаления требует отдельного решения.

## Проверки для сопровождающего

Из `products/harness-platform`, в закреплённом runtime:

Рядом с корнем нового исходного дерева необходим каталог `baseline` из
snapshot commit `02a2efdbbe716fcf642ebf9aaf12f30ddea6476f`. Он включён в ZIP
только как вход проверки обновления; при Git checkout создаётся через
`git worktree add --detach ../baseline` с указанным commit из корня репозитория.
Без этого входа тест обновления явно skip, и полный gate не принимается.

```bash
export HARNESS_DIALOG_ENGINE=native
python acceptance/run_workshop_python.py --result /absolute/evidence/python.json
python acceptance/run_workshop_browser.py --result /absolute/evidence/browser.json
node --test native/*.test.mjs
```

Для браузеров явно задаются `PLAYWRIGHT_CHROMIUM_EXECUTABLE_PATH` и каталог
evidence. Opera запускается своим настоящим бинарником, с теми же тестами;
смена user agent не заменяет проверку браузера. Harness находится через
`HARNESS_NODE_MODULES`, Python native helper — через `HARNESS_TEST_PYTHON`.
Для принятой Opera необходим режим `--headed` и Xvfb; точные команды обоих
browser runners приведены в корневом README. Он сохраняет настоящие события
ввода и проверки прокрутки, которые не поддержал headless-режим этой версии.
Подробный запуск live-проверки имеет отдельный бюджет, exact source digest,
синтетический аккаунт и запрет повторов при неизвестной стоимости.
