# Количественные адаптеры маркетплейсов: контракты и источники

Версия паспортов: `2026-11-28.1`. Дата проверки первичных источников: 28 ноября 2026 года.

Этот документ сопровождает `platform_core/market_quantity_registry.py` и `platform_core/market_quantity_providers.py`. Он не является актом живой приёмки. Синтетические ответы в `tests/fixtures/market_quantity_cases.py` воспроизводят формы документированных контрактов и отдельно описанные фактически наблюдённые структуры; значения в них вымышлены. `live_verified=false` в статическом паспорте не подменяется результатом модульного теста: реальные вызовы подтверждаются отдельными журналами авторизованной проверки.

## Граница исполнения

Адаптеры являются функциями `request(template_id, checkpoint, context)` и `consume(template_id, checkpoint, context, response)`. Они не выполняют HTTP, SQL, вызовы модели, начисление расходов или ожидание. `market_quantity_runtime.Backend`, подключённый к существующему `market_collect.Collector`, владеет HTTP, разрешениями, лимитами, lease, журналом и атомарным подтверждением страниц. Ключи остаются в зашифрованном хранилище и не передаются адаптерам.

Контрольная точка содержит стадию, курсор, счётчики, отпечаток привязки подключения и периода, идентификатор созданного отчёта. Подписанная ссылка временно сохраняется только в приватной контрольной точке. Скачивание не передаёт API-ключи и не следует перенаправлениям; исполнитель отдельно проверяет DNS. После истечения ссылки повторно опрашивается сохранённый идентификатор отчёта.

Идентификаторы кабинета, кампании, продавца, отчёта, отправления и токен продолжения являются серверными параметрами. Они не расширяют пользовательский инструмент произвольными URL, SQL, путями или API-операциями. Контрольная точка привязана к подключению, его поколению, продавцу, периоду и дополнительным селекторам. Смена ключа или магазина не может продолжить прежнюю задачу.

## Лимиты, отдельные стадии и HTTP 429

Паспорта содержат исполняемые `min_interval`, `max_concurrency`, `max_active_retries`, `max_cycle_seconds`, backoff, список заголовков и общую политику ошибок. Локальная последовательная отправка намеренно не использует разрешённый burst. Перестановка ключей одного продавца не создаёт новую квоту.

### Wildberries

| Шаблон/стадия | Персональный / сервисный токен: минимальный интервал | Базовый без сервисного секрета |
| --- | --- | --- |
| WB-01 seller-info | 60 секунд | 24 часа |
| WB-02 cards/list | 0,75 секунды | 0,75 секунды |
| WB-03 sales-funnel | 20 секунд | 30 минут |
| WB-04 detailed | 60 секунд | 12 часов: 2 запроса за 24 часа |
| WB-05 generate | 60 секунд | 15 минут |
| WB-05 status | 5 секунд | 15 минут |
| WB-05 download | 60 секунд | 15 минут |

Источник каждой строки — соответствующая официальная OpenAPI-спецификация WB из таблицы контрольных сумм ниже. Сервисная квота дополнительно объединяет токены одного зарегистрированного сервиса. Стандартная классификация неизвестного токена — базовый, без ослабления ограничений.

Официальный `01-general.yaml` документирует claims JWT: `acc=1` без `for` и `t=false` — базовый; `acc=2` и `t=true` — песочница; `acc=3`, `for=self`, `t=false` — персональный; `acc=4`, `for=asid:{Service ID}`, `t=false` — сервисный. `wb_token_profile` разбирает только эти документированные признаки и s/exp/sid, не возвращая исходный токен. Повышенная квота применяется только после успешного seller-info тем же токеном с совпадением sid. Декодирование без проверки сервера не подтверждает подлинность JWT. Неизвестный формат остаётся базовым.

Для 429 сохраняется наибольшая из применимых задержек: локальный интервал, backoff, Retry-After, `X-Ratelimit-Retry`, `X-Ratelimit-Reset`. Значения Retry/Reset у WB означают оставшиеся секунды, а не Unix-время. Заголовки Remaining/Limit описывают burst и не разрешают игнорировать установленную задержку. Описание: [официальная информация WB API](https://dev.wildberries.ru/api/swagger/yaml/en/01-general.yaml).

### Яндекс Маркет

| Метод/шаблон | Базовая документированная квота | Последовательный интервал |
| --- | --- | --- |
| Token info | 100 запросов/час | 36 с |
| Campaigns | 1000/час | 3,6 с |
| Offer mappings | 100/мин | 0,6 с |
| Business orders | 10000/час | 0,36 с |
| Returns | 5000/час | 0,72 с |
| Warehouse discovery v2/v3 | 100 запросов/час | 36 с на метод |
| Generate реализации и вариантов остатков | 1 запрос/2 минуты | 120 с на метод |
| Общий report info | 100/мин | 0,6 с общей очереди |

Верхний предел параллелизма — 4 для соответствующего кабинета/магазина; локальный паспорт каждого метода дополнительно сериализован. У Маркета quota error включает **HTTP 420**, поэтому политика обрабатывает 420 и 429. `X-RateLimit-Resource-Until` — абсолютная HTTP-дата. Из-за истечения 60-минутной ссылки вызывается report info сохранённого report ID. Источники: [лимиты](https://yandex.ru/dev/market/partner-api/doc/ru/concepts/limits), [report info](https://yandex.ru/dev/market/partner-api/doc/ru/reference/reports/getReportInfo), [token info](https://yandex.ru/dev/market/partner-api/doc/ru/reference/auth/getAuthTokenInfo), [campaigns](https://yandex.ru/dev/market/partner-api/doc/ru/reference/campaigns/getCampaigns).

Квоты с платной подпиской не предполагаются. Скачивание сформированного файла не приравнивается к новому запуску генерации.

У актуального отчёта остатков для FBS/DBS/Express без групп складов отдельный путь v3, который принимает `partnerWarehouseIds`, а не `campaignIds`. Адаптер сначала проходит все страницы warehouse discovery. Идентификатор кампании должен быть прямо подтверждён в `models[].campaignId` для нужной модели. Неоднозначная связь, пустой справочник или неизвестная модель не превращаются в нулевой остаток. Для групп используется отдельный campaign-filtered discovery v2 с `groupInfo`. Существующий FAILED старого неселективного маршрута сохраняется в checkpoint; допустим только переход к discovery нового маршрута, без повторного создания того же старого отчёта. Источники: [текущие склады](https://yandex.ru/dev/market/partner-api/doc/ru/reference/warehouses/getPartnerWarehouses), [группы складов](https://yandex.ru/dev/market/partner-api/doc/ru/reference/warehouses/getPagedWarehouses), [текущий отчёт остатков](https://yandex.ru/dev/market/partner-api/doc/ru/reference/reports/generateStocksReport), [отчёт групп и FBY](https://yandex.ru/dev/market/partner-api/doc/ru/reference/reports/generateStocksOnWarehousesReport).

Явный `NO_DATA` при конечном `DONE` либо `FAILED` учитывается отдельно от отсутствующего файла. Он подтверждает только запрошенный и проверенный период/магазин; `PROCESSING/NO_DATA` не завершает сбор, а `DONE` без файла и без `NO_DATA` считается ошибкой схемы. Источник: [report info и независимый subStatus](https://yandex.ru/dev/market/partner-api/doc/ru/reference/reports/getReportInfo). Во время авторизованной проверки 28 ноября 2026 года YM-05 фактически вернул `DONE/NO_DATA`; свидетельство хранится отдельно в журнале live.

Во время той же проверки текущий YM-06 прошёл discovery, генерацию v3 и report info с `DONE`; авторизованный report info выдал файловый хост `market-mbi-prod.s3-private.mds.yandex.net`. Разрешён именно этот хост, без расширения до произвольного внешнего URL. Подписанный query должен сохраняться при HTTP-скачивании; передача пустого `params={}` в httpx уничтожает подпись, что проверяется отдельным тестом общего исполнителя.

В реально скачанном v3 ZIP оказался один CSV с `SHOP_SKU`, `PRODUCT_NAME`, `ERRORS`, `COUNT`, `RESERVE`, `WAREHOUSE`, без `PLACEMENT_TYPE`. Документация в этот момент продолжала показывать `stocks_business` с `WAREHOUSE_AND_SHOP` и `PLACEMENT_TYPE`, одновременно предупреждая об изменяемой структуре отчётов. Адаптер распознаёт обе явные сигнатуры. Вариант без `PLACEMENT_TYPE` допускается только при доказанной единой кампании **всех** моделей выбранных складов. Несколько CSV, неполный набор колонок, неизвестная модель или неоднозначное владение не принимаются. Старая контрольная точка может заново проверить scope и продолжить тот же report ID; она не создаёт отчёт повторно. Структурные свидетельства сохранены в live-запусках `20261128T032144Z` и `20261128T032341Z`; содержимое товаров и подписанные URL в них отсутствуют.

### Ozon

Из первичных материалов подтверждены общая квота Seller API по Client-Id и новые заголовки `Ratelimit-Remaining` / `Retry-After`. Однако актуальные индивидуальные квоты всех используемых методов из интерактивной страницы Seller API в этой сессии не были прочитаны: страница не отдала пригодный полный контракт. Поэтому `documented=false` у индивидуальных профилей; локальные потолки — 1 запрос/секунду для чтения, 1 генерация/минуту на метод. Эти значения являются консервативными настройками исполнения, **не заявленной квотой провайдера**. Актуальные ограничения метода должны быть подтверждены отдельно, а ответ провайдера всегда может увеличить задержку. Источники: [новые заголовки](https://dev.ozon.ru/news/802-Zagolovki-dlia-upravleniia-reit-limitami-v-Seller-API/), [разъяснение общей квоты](https://dev.ozon.ru/community/2373-HTTP-429-na-finansovykh-metodakh-Seller-API-pri-redkikh-zaprosakh/).

Авторизованный report info вернул файловый хост `ir.ozone.ru`. Он добавлен как точный разрешённый хост из уже доверенного общим Octoport runtime домена `ozone.ru`. Подписанные пути и query не выходят в публичное свидетельство, API-заголовки в запрос файла не передаются. Идентификатор отчёта допускает только `[A-Za-z0-9_.:-]{1,255}`, поэтому URL или произвольная строка не принимаются вместо report ID.

Страница Seller API Ozon при повторной проверке осталась без читаемого содержимого. Первичные публикации Ozon подтверждают версии posting API и общую Client-Id квоту, но не заменяют индивидуальную квоту каждого метода и точную минимальную роль. Поэтому `required_scope_evidence` у Ozon честно отмечает role hint из действующего runtime, а не заявляет документальное подтверждение. Это конкретный незакрытый пункт MP-T03.

Ни текущие 30 дней, ни пустой старый месяц не доказывают полный backfill. Источники с UNKNOWN должны сохранять этот статус до установленной провайдером границы. Ветки YM06 для FBY, групп складов и нескольких кампаний проверяются контрактными сценариями; имеющийся авторизованный FBS-магазин не может дать живое доказательство всех этих альтернативных моделей.

## Семантика количеств

`quantity_basis` определяет сопоставимость: `order_cohort`, `funnel_interval`, `calendar_event`, `return_event`, `stock_snapshot`. Неизвестное количество записывается как `null`, а не как ноль. У исходного заказа сохраняются ordered_qty и ordered_at независимо от поздних исходов.

WB cancelCount включает отмены и возвраты. Оно не подменяет physical_return_qty и не разрешает начислять коэффициент брака возвратов на все потери. buyoutCount хранится отдельно; его нельзя без доказательства переименовать в валовую физическую доставку. Агрегат точного интервала не разворачивается в придуманные дневные заказы. Основание — описание selectedPeriod/orderCount/buyoutCount/cancelCount в официальном [analytics OpenAPI](https://dev.wildberries.ru/api/swagger/yaml/en/11-analytics.yaml).

В детализации WB сохраняются количественные операции «Продажа»/«Возврат» с rrdId и датой реализации. Логистика, выплаты, комиссии и прочие финансовые корректировки не становятся продажами. int64 reportId хранится строкой без потери точности. Заказная дата из этой детализации сама по себе не восстанавливает исходный объём всех заказов.

Операция WB «Возврат» сохраняется в `calendar_return_qty` для календарного net. Она не доказывает физическую логистическую приёмку товара: `physical_return_qty=null` и `physical_returns_known=false`. Коэффициент брака возвратов нельзя применять к этому количеству как к доказанным физическим возвратам. Официальный финансовый контракт описывает реализационный документ и операцию, без отдельной стадии логистического возврата.

Ozon сохраняет уникальные экземпляры возвратов и привязку `(scheme, posting_number, SKU)` для принятого общего physical_outcome_union. Cancellation/FullReturn/PartialReturn нельзя автоматически объявлять физическими возвратами покупателя после покупки. Физический ClientReturn дополнительно требует подтверждённой стадии логистического получения; отменённая/отклонённая заявка имеет нулевой эффект и остаётся прослеживаемой. Ozon отдельно описывает дополнительное отменённое отправление при частичном отказе — его нельзя суммировать с исходным заказом без проверки связи. [Официальное описание частичного отказа](https://dev.ozon.ru/start/448-Spravochnik-metodov-Seller-API-dlia-Ozon-Logistiki/).

У Маркета `itemStatuses` проверяются по сумме count исходной позиции. Если статусы отсутствуют или покрывают не всё количество, исходное количество остаётся известным, а исходы — неизвестными. В returns `fastReturn=true` означает возврат денег без возврата товара; refundStatus сам по себе не доказывает физическое поступление. RETURN и UNREDEEMED не сливаются. Месячные листы delivered/returned/unredeemed остаются календарными событиями. Источники: [заказы](https://yandex.ru/dev/market/partner-api/doc/ru/reference/orders/getBusinessOrders), [возвраты](https://yandex.ru/dev/market/partner-api/doc/ru/reference/returns/getReturns).

В YM03 явно передаётся `sourcePlatforms=["MARKET"]`, а ответ с явным sourcePlatform `OZON`, `WILDBERRIES`, `OTHER` или неизвестным значением отклоняется. Это исключает повторный учёт заказов сторонних площадок, обслуживаемых через LaaS Маркета. Отсутствие необязательного поля в ответе не отменяет серверный фильтр запроса. Источник — тот же актуальный контракт getBusinessOrders.

Остатки не суммируются с продажами. В WB сводная строка «всего», отдельные склады и товары в пути имеют разные stock_kind. В YM FBY VALID/RESERVED/AVAILABLE_FOR_ORDER различаются; FBS COUNT означает доступное количество. Фильтр `hasStocks=false` не устанавливается, потому что это ограничило бы выборку товарами без остатков. Источник: [отчёт по остаткам Маркета](https://yandex.ru/dev/market/partner-api/doc/ru/reference/reports/generateStocksOnWarehousesReport).

## Проверки и применимость

`python -m unittest tests.test_market_quantity_providers -v` проверяет каждый из 18 обработчиков, отсутствие PII/денег/ключей в проекции, паспорт квот, JSON-контрольные точки, сохранение ID отчёта, обе схемы Ozon, курсоры, повторы страниц, конечный 204 WB, неизвестные значения, физические и календарные исходы, архивы и приватность ссылок.

`tests/fixtures/market_quantity_cases.py` используется также испытаниями реального общего Backend и durable limiter через локальный HTTP-стенд. Тесты 429/5xx/обрывов, рестартов, отзыва поколения и квот исполнителя находятся в `tests/test_market_quantity_runtime.py`. Прямой вызов consume с HTTP 429 проверяет отказ принимать ошибку за успешные данные; саму задержку и восстановление проверяет исполнитель, не адаптер.

`acceptance/market_quantity_live.py` дополнительно считает независимые исходные количества прямо из ответов API/CSV и сверяет их с локальной проекцией по атомарному receipt. Это позволяет проверить сохранение заказанных единиц, количественных реализационных операций, остатков, числа строк и уникальных экземпляров возвратов. Счётчики не вызывают адаптер и не используют модель. Повторный HTTP одной ступени не удваивает сверку: участвуют только подтверждённые шаги текущего epoch. Если не все шаги наблюдались в данном запуске, результат явно `NOT_FULLY_OBSERVED_THIS_RUN`. Это API→локальная сверка; она не заменяет сверку с интерфейсом кабинета продавца и не доказывает семантику неизвестного физического исхода.

У JSON-шаблона повреждение ZIP неприменимо, но повреждение JSON обязательно. Генерация с неизвестным исходом неприменима к шаблону без генерации. Для генерации после timeout/5xx/обрыва запрещён слепой повтор: создаётся `uncertain`, а сохранённый report ID при наличии используется повторно. Для WB-05 это относится и к GET создания отчёта. Неприменимость не заменяет живую проверку.

Оставшиеся необходимые внешние доказательства: успешные авторизованные ответы каждого применимого этапа; реальные права и классы токенов; подтверждение индивидуальных Ozon-квот и retention-границ, где они доступны; сверка количеств с кабинетами; полный backfill и покрытия; независимые браузерные и хозяйственные регрессии. Успех модульных тестов не закрывает эти пункты автоматически.
