## Как обеспечена согласованность

До открытия SQLite read snapshots зафиксированы состав, атрибуты и SHA256 включённых исходных файлов. Затем каждая база открыта `mode=ro`, `query_only=ON`; удерживались read transactions, использовался штатный SQLite backup API. Для каждой базы сопоставлены структура, все значения строк и количества; результаты integrity и FK проверены до принятия копии.

Остальные собственные state/config/key files скопированы побайтно и проверены по fingerprints источника. Повторная проверка всех источников выполнена после копирования и после restore proof. Исходные файлы, конфигурация и процесс не изменились, поэтому получена согласованная точка без остановки Master. При изменении состава/содержимого source этот helper выдаёт отказ и не обозначает архив как принятый согласованный snapshot.

SQLite-файлы в архиве самостоятельные: данные перенесены backup API в отдельные базы. WAL, SHM и journal исходных баз используются для контроля согласованности, но не подмешиваются при восстановлении рядом с новыми базами. SHM исключён из устойчивого source fingerprint как служебное состояние SQLite locks.

Архив распакован с безопасным tar filter в отдельный каталог:

`/opt/podmasterye/backups/master-full-transfer-20261127-115047-033921/restore-proof`

Каталог закрыт правами 0700. Повторно проверены hashes восстановленных файлов, SQLite schema/data fingerprints, counts, integrity и FK. Приложение, таймеры, Telegram и обращения к провайдерам из восстановленной копии не запускались. Проверка подтверждает сохранность данных и конфигурации; исходный production продолжал работу.

## Подготовленная процедура перед будущим выпуском

1. Зафиксировать code/runtime commit, исходные service/config paths и набор финансовых/предметных invariants. Подготовить релиз и соответствующие архивы прежнего кода отдельно от данных.
2. В согласованном окне финального выпуска приостановить только Master и создать **новый полный закрытый backup** актуального state/config. Снимок от 16:50:47 UTC+5 — проверенный резервный рубеж на указанное время; перед будущим deployment требуется свежий backup после согласованной паузы.
3. Сохранить архив с правами 0600 в новом каталоге 0700; записать его SHA256, counts и integrity/FK. Секретные fingerprints хранить только в закрытом manifest на Alisa.
4. Повторить restore proof в отдельном новом закрытом каталоге. Проверить byte hashes и все SQLite invariants до переключения данных. Для испытания startup использовать обезличенную копию без действующих ключей и внешних отправок, как в выполненном migration rehearsal.
5. Применять согласованный релиз только после успешных backup, restore и миграционных gates. Полные архивы данных, секреты и закрытые private manifests не входят в Git, ZIP с кодом, публичные artifacts или Library.

Эти действия будущего выпуска здесь не исполнялись: текущая проверка выполняла только read-only snapshot production и работу с закрытыми копиями.

## Процедура фактического восстановления при необходимости

Восстановление production выполняется координатором в согласованном окне с остановленным только Master. Сначала проверяются SHA256 выбранного архива и соответствующая версия кода/runtime. Текущее состояние сохраняется отдельным закрытым резервом для расследования.

Архив распаковывается в новый закрытый staging-каталог с tar filter `data`. Проверяются hashes по private manifest, SQLite integrity/FK/counts, наличие исходных auth/encryption/config files. Для окончательного размещения восстанавливаются владельцы и права по private manifest и действующей модели systemd StateDirectory; архивные root-only копии не используются как готовое рабочее размещение без этой проверки.

Далее согласованно заменяются собственные state/config Master и соответствующая версия кода. Используются самостоятельные SQLite backup files без устаревших WAL/SHM/journal из другого состояния. После запуска Master проверяются доступность, авторизация, разрешённые маршруты, финансовые/предметные invariants и отсутствие незапланированных внешних отправок. Затрагивать Octoport или общий runtime для восстановления этого state/config не требуется.

Фактическая запись в production, восстановление поверх действующих данных и запуск приложения из raw backup в рамках этой приёмки не выполнялись.
